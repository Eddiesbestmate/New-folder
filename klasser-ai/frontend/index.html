What it does

Built for the way schools actually timetable

Questions

The things schools ask first

What if the timetable it produces is wrong?

It does not reach you. Every hard rule — teacher and room double-bookings, student clashes, room capacity, teacher qualifications and availability — is checked by deterministic code, not by the AI. Four AI validators then review the result separately, and any one of them failing sends the run back to the layer responsible. The deterministic checker can never be overruled.

Do I pay for a run that fails?

No. Credits are held when a run starts and only settled when a timetable is actually produced. If it fails, the hold is released and the reason recorded — whoever's fault it was.

Can I change the timetable after it is generated?

Yes, in plain English. Describe the change and Klasser shows you what it would do, checked against every rule, as a before-and-after diff. Asking costs nothing; you are only charged if you apply it. Your published timetable is never edited in place — changes go into a new version you choose to publish.

We have two campuses and students who move between them.

That is solved as part of the timetable rather than afterwards. Klasser works out who needs to travel and when, assigns buses within their capacity, and schedules the empty repositioning legs too. Departure times are calculated backwards from the bell using your real travel times.

Will it work with our existing systems?

Import takes the spreadsheets you already keep. For export, paste the header row your system expects and Klasser maps it to the right fields once — after that, every export is instant and in exactly that format.

Is our data kept separate from other schools?

Yes, and enforced in the database rather than only in application code. Every table carrying school data has row-level security, so a query can only ever return your own school's rows — a mistake in an API call cannot leak across schools.
